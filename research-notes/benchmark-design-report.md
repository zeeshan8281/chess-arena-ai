# A benchmark that separates chess agents

AS_OF: 2026-10-14. Research artifact for Chess Arena's local benchmark revision. This report synthesizes the two research-note files and does not claim that the proposed tests have finished running. It separates cited findings from implementation recommendations. The numbered references resolve through registry.md and direct source links below.

## 1. What the 100% scores actually tell us

**Confidence: high for the diagnosis; medium for the best replacement design.** Beating a random-move opponent consistently establishes that a configuration can exploit that opponent under the arena's rules. It does not establish perfect chess ability, distinguish two configurations that both pass the gate, or justify a general strength ranking. The relevant research makes precisely this distinction: LLM CHESS uses random opponents as a cost-effective initial gate, then evaluates promising models against an engine with variable skill. Its objective for the first stage is basic completion and instruction following, rather than precise ranking of strong models. [1] ([LLM CHESS](https://arxiv.org/abs/2512.01992), 2025-12-01.)

The product implication is to preserve the existing result but rename its purpose. “Random-opponent completion” or “Regression games” accurately describes a useful check. It should not be the headline measure of how strong an agent is. A user comparing several 100% results needs a harder common task, richer behavioral measurements, or both. The solution is not to alter the scoring formula until the chart looks more varied. A benchmark must accept ties when the observations justify them; the task distribution should be chosen before seeing the results. This is our design recommendation, based on the staged evaluation structure above.

Head-to-head play is another established way to increase meaningful competition. DeepMind describes Game Arena's chess evaluation as games between models, with opposition that develops alongside the model pool. Its public harness also makes the surrounding game environment, prompt generation, sampling and parsing explicit. These examples support a platform built around reproducible competitive configurations rather than a single attractive chart. They do not establish that Chess Arena already reproduces Game Arena's settings or ratings. [2][3] ([Game Arena harness](https://github.com/google-deepmind/game_arena/blob/main/README.md), observed 2026-10-14; [official platform update](https://blog.google/innovation-and-ai/models-and-research/google-deepmind/kaggle-game-arena-updates/), 2026-02-02.)

There is an important counterpoint: random play is not useless just because capable agents saturate it. It remains inexpensive, replayable and sensitive to some operational failures. Removing it would discard a useful regression signal. The proposed change is therefore a separation of tracks: keep that gate, introduce a discriminating position pilot now, and develop stronger full-game evaluation separately. Those tracks answer different questions and should retain different labels.

## 2. A practical first pilot: 32 positions, four difficulty bands

**Confidence: high for data-format requirements; medium for the proposed sample.** The immediate proposal is a frozen set of 32 first-move problems: eight each in source puzzle-rating bands 800–1199, 1200–1599, 1600–1999 and 2000–2600. These numbers are a practical pilot design, not a published standard or proof of sufficient statistical power. Lichess provides puzzle ratings, rating deviation, themes and other metadata under CC0, making transparent stratification possible. The Kagi chess-puzzle project also exposes a small existing Lichess-derived artifact suitable for an affordable initial investigation. [4][5] ([Lichess database](https://database.lichess.org/), dataset dated 2026-10-05; [Kagi puzzle project](https://github.com/kagisearch/llm-chess-puzzles), README dated 2025-04-26.)

Choose the entire manifest before any model calls. Record the source artifact, its hash, selection code, filter rules, random seed where applicable, puzzle IDs, ratings and themes. Store the exact input position and expected answer. A later run should be able to identify whether it used precisely the same tasks. Do not replace an awkward item because a favored model fails it, or because all models solve it. Any correction to an invalid fixture should create a documented suite revision and trigger consistent rescoring or rerunning across configurations.

The input-position convention is essential. In the Lichess format, the FEN precedes an opponent setup move. Apply the first move in the solution list before asking the model to solve the puzzle; the next move begins the solver's answer. Querying the original FEN would test a different task. The documentation also warns that a mate-in-one can have more than one valid mating move. A scorer should accept a legal move that actually delivers checkmate in that case, rather than reject it merely because it differs from the stored line. [4] ([Lichess puzzle format](https://database.lichess.org/), observed 2026-10-14.)

Call the metric “first-move accuracy,” not chess Elo or overall game strength. A correct first move is useful evidence about tactical choice, but does not prove that an agent can convert the ensuing position, defend an inferior position, or avoid repeating itself across a long game. The LLM CHESS paper explicitly evaluates interaction across full games and includes per-ply and per-game behaviors. Its broader scope explains why a cheap position test should complement rather than replace full-game evidence. [1] ([LLM CHESS](https://arxiv.org/abs/2512.01992), 2025-12-01.)

The band labels must describe their provenance. They are Lichess puzzle ratings, not the tested model's Elo. They need not produce monotonically decreasing model scores: a small hard-band sample could happen to contain patterns a model recognizes well. Public puzzles also carry contamination risk, which the Kagi project acknowledges. The pilot should state that it is public, small and exploratory; later versions should add fresh held-out positions and maintain a separate development set. [4][5] ([Lichess](https://database.lichess.org/); [Kagi](https://github.com/kagisearch/llm-chess-puzzles)).

The table is a candidate list, not a leaderboard. Pricing may vary with provider, cache and context behavior, so the final cost chart should use billed usage from each response. The inventory also lists Gemini 2.5 Flash-Lite as an inexpensive alternative, but adding another candidate should not silently replace a failed run or obscure the predefined comparison. Five model families or configurations are sufficient for this initial local implementation; broader coverage can follow a versioned procedure. [6] ([Models API](https://openrouter.ai/api/v1/models), observed 2026-10-14.)

A configuration is the model plus its surrounding harness: prompt, representation, legal-move assistance, memory, reasoning setting, output cap, timeout, retries and parser. The Game Arena repository implements multiple board representations, legal-move inclusion, majority voting and rethinking after illegal moves. Those choices can change behavior. LLM CHESS also reports sensitivity to how board and legal-move information are supplied. Therefore, publish the configuration name and hash alongside the model name; do not portray a model assisted by search as equivalent to the same model making an unaided choice. [1][2] ([LLM CHESS](https://arxiv.org/abs/2512.01992); [Game Arena harness](https://github.com/google-deepmind/game_arena/blob/main/README.md)).

The pilot should use a shared prompt and post-setup FEN, with the same legal-move representation and parser. If every model is given all legal moves, say “legal-move selection” or explain that assistance in the methodology. If a local helper chooses a fallback after a bad model response, record that intervention independently and do not credit its answer to the model's first attempt. This is a proposed scoring rule, motivated by the explicit distinction between models and harness components in the cited implementations.

Equal output-token limits do not imply equal inference compute. OpenRouter's documentation explains that reasoning tokens are billed and usually share the output limit with the visible answer. A small cap can be consumed entirely by reasoning, leaving empty content. Supported reasoning controls differ by model, and a low effort label is not a portable numeric budget. Use each model's supported parameters, publish the actual choice, and record truncation rather than hiding it. The observed Luna and Haiku 5.5 listings do not include temperature among supported parameters, so a universal request body should not assume that knob exists. [6][7] ([Models API](https://openrouter.ai/api/v1/models); [Reasoning Tokens](https://github.com/OpenRouterTeam/docs/blob/main/guides/best-practices/reasoning-tokens.mdx), observed/updated 2026-10-14.)

## 4. Honest scoring and graphs

**Confidence: high for statistical principles; medium for a 32-item descriptive pilot.** The primary numerator is correctly solved positions. A completed run's denominator is all 32 scheduled positions, including wrong legal answers and recorded failures. The artifact should distinguish wrong move, illegal move, parse failure, API error, timeout and truncation. Unattempted items indicate an incomplete run, which must not be compared on the same headline frontier as fully completed runs. This denominator policy is an implementation recommendation, not a claim that every cited benchmark makes the same choice.

Show absolute counts next to percentages. “24/32” is more informative than a bare “75%,” and “8/8 in this band” conveys the actual amount of evidence behind a perfect observation. NIST describes Wilson and exact binomial confidence-interval methods suitable for bounded proportions and small or extreme samples. The proposal is to show Wilson 95% intervals for simple descriptive accuracy, while acknowledging that a deliberately stratified and potentially correlated puzzle set is not a random sample of all chess positions. [8] ([NIST confidence intervals](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm), undated foundational guidance, read 2026-10-14.)

For illustration, the task-design notes calculate a two-sided Wilson interval of approximately 67.6–100% for eight successes out of eight. That calculation shows why an observed 100% does not establish perfect underlying performance; it is not an actual model result from the ongoing pilot. For the same reason, a one-item lead on 32 positions should not become a confident “best model” badge. Later comparisons should preserve shared item IDs and difficulty strata so paired differences or an appropriately designed bootstrap can quantify uncertainty between configurations. [8] ([NIST](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm)); paired-comparison procedure is our proposed next step.

The homepage can then present three views: overall first-move accuracy with sample counts, accuracy by difficulty band, and an observed cost–accuracy or latency–accuracy scatterplot. A Pareto frontier is appropriate only among completed configurations evaluated on the same suite version and scoring rules. Label the axes explicitly: cost per attempted position or median latency per response, not a vague “cost” or “speed.” Distinguish local executable baselines from paid model calls because zero API spend does not mean zero compute expense.

A frontier line describes the recorded sample; it is not a statistical claim that every point on it is truly superior. Keep overlapping observations visible through selection, a companion table or collision-free labels, without moving their actual plotted coordinates. Selecting a point should show its configuration, counts, errors, interval, cost, latency and evidence link. Raw-model results and custom harness results may share a display if the distinction is explicit, but users also need filters to avoid confusing model choice with engine assistance. These are product recommendations derived from the transparency needs above, not external benchmark findings.

## 5. The next stage: stronger, controlled full games

**Confidence: high that opponent and match controls matter; medium on the exact ladder to adopt.** After the pilot, add a full-game ladder with several executable opponents. The goal is to cover an informative difficulty range, not to replace universal wins against random with universal losses against maximum-strength Stockfish. The LLM CHESS design demonstrates the logic of progressing promising models to stronger engine opponents. Stockfish's FAQ also explains that rating depends on opponent pool and match conditions, so a small local experiment cannot establish a universal human-equivalent Elo. [1][9] ([LLM CHESS](https://arxiv.org/abs/2512.01992); [Stockfish FAQ](https://official-stockfish.github.io/docs/stockfish-wiki/Stockfish-FAQ.html), read 2026-10-14.)

Pin the engine binary and network hash, engine options, thread count, node budget, opening manifest, move limits, timeout and adjudication rules. Fastchess supports fixed-node testing, openings, color-swapped pairs and PGN output. Those features provide a concrete implementation reference for repeatable match scheduling and evidence capture. A practical arena can adopt the same control principles without claiming that its scheduler or resulting ratings are identical to Fastchess experiments. [10] ([Fastchess manual](https://github.com/Disservin/fastchess/blob/master/man.md), file commit 2026-10-04.)

Each opening should be played with colors reversed under the same conditions. Keep opening selection fixed for a suite and isolate tuning openings from held-out evaluation openings. Include endgame conversion and defensive positions so an agent cannot look strong only through opening familiarity. These are proposals for broadening the task mix; neither the sources nor this report establish the ideal number of openings for the arena's eventual population.

Do not present nominal search depth as a simple amount of exhaustive computation. Stockfish documents pruning, reductions and extensions that make depth an imperfect description of actual work. Its weakened skill modes also introduce randomized selection of weaker moves. Fixed node budgets, pinned options and clearly named opponent tiers are therefore preferable to unexplained labels such as “1500 Elo opponent.” If an engine-strength label is used, disclose precisely how it was calibrated and against which pool. [9] ([Stockfish FAQ](https://official-stockfish.github.io/docs/stockfish-wiki/Stockfish-FAQ.html), observed 2026-10-14.)

Retain outcome and behavior separately: wins, draws, losses, stopped games, instruction failures and model-service failures. Add engine-derived move-quality or conversion measures only with explicit analysis settings. An adjudicated result, a move-limit stop and a rules-defined draw are different events. The LLM CHESS paper itself uses different model-error handling across stages, illustrating why our own policy must be written rather than assumed from a borrowed metric name. [1] ([LLM CHESS](https://arxiv.org/abs/2512.01992), 2025-12-01.)

The current official Stockfish UCI implementation provides a more concrete integration check than a general claim of engine support. Its command parser reads a node limit, its new-game command clears search state, and its search updates emit node count, speed, hash occupancy, tablebase hits, time and principal variation. Those code paths support an auditable adapter, but reading them is not a guarantee of determinism across machines or binaries. The engine version used by the arena still needs to be pinned and tested. [12] ([Stockfish UCI implementation](https://github.com/official-stockfish/Stockfish/blob/master/src/uci.cpp), complete displayed file read 2026-10-14; exact commit date not captured.)

Our proposed adapter acceptance check is to retain the command transcript beside each game, including the options and search limits actually sent. Confirm that each search produces a terminal best-move response, that independent trials reset search state according to the documented policy, and that a timeout cannot be mistaken for a draw. Save returned analysis fields rather than reconstructing them from wall-clock estimates. A malformed position, crashed process and exhausted move limit should each retain a distinct status. These are implementation requirements for future work; this research did not execute a Stockfish binary or verify an arena adapter.

## 6. Evidence, budget and delivery requirements

**Confidence: high for operational requirements; actual run completion remains unverified here.** Every published result needs an immutable evidence artifact: suite hash, model and provider identity, configuration hash, exact prompt or prompt template, task IDs, requested settings, timestamps, parsed answers, statuses, token usage and billed costs. Full-game artifacts should additionally preserve move sequences, starting and final positions, game results and replayable PGNs. This is the proposed acceptance contract for the local implementation, informed by the reproducible harness and game-run tooling described above. [2][10] ([Game Arena](https://github.com/google-deepmind/game_arena/blob/main/README.md); [Fastchess](https://github.com/Disservin/fastchess/blob/master/man.md)).

The user's persistent total API limit is $5. Research did not make paid requests. Before any benchmark batch, implementation should reconcile accumulated usage, calculate remaining allowance, reserve conservative per-call spend before concurrency and stop when that allowance would be exceeded. OpenRouter documents key usage and remaining-budget fields, plus in-flight reservation and settlement behavior. Provider-side controls are useful, but the experiment still needs its own ledger because a local allowance may be stricter than the account's available balance. [11] ([OpenRouter Limits](https://github.com/OpenRouterTeam/docs/blob/main/api_reference/limits.mdx), observed 2026-10-14.)

The five candidate configurations are chosen to make diverse actual measurements affordable. The report does not guarantee that a particular number of requests will fit the remaining balance: reasoning, input length, retries and provider behavior affect realized cost. If budget prevents completing a configuration, keep the evidence and label it incomplete. Do not substitute a synthetic score, borrow a number from an unrelated leaderboard, or silently remove a failed candidate to make the page cleaner.

Local acceptance should check that every scheduled task has a terminal status, every displayed percentage matches raw records, every puzzle setup is valid, alternative mate-in-one answers are handled, and costs and durations aggregate correctly. Verify the chart against the artifact and inspect the actual page at desktop and mobile sizes. Source-based methodology improvements do not replace application testing, and a successful build does not establish that a benchmark ran. These checks are proposed requirements; the parent implementation must report which it actually completed.

## 7. Counter-review, confidence and remaining work

At least six material objections survive the synthesis. First, a public first-move suite may reward memorization and cannot establish long-horizon play. Second, human puzzle ratings need not predict model difficulty. Third, equal token ceilings do not equalize compute. Fourth, tiny samples and correlated themes limit ranking precision. Fifth, engine assistance can dominate a model's contribution unless tracks are labeled. Sixth, increasing opponent strength can create a floor where every system fails. The proposed controls reduce these problems but do not eliminate them. [1][4][5][7][8][9] ([LLM CHESS](https://arxiv.org/abs/2512.01992), [Lichess](https://database.lichess.org/), [Kagi](https://github.com/kagisearch/llm-chess-puzzles), [OpenRouter reasoning](https://github.com/OpenRouterTeam/docs/blob/main/guides/best-practices/reasoning-tokens.mdx), [NIST](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm), [Stockfish](https://official-stockfish.github.io/docs/stockfish-wiki/Stockfish-FAQ.html)).

The actionable near-term result is a clearly labeled 32-position pilot with multiple measured model configurations, executable baselines, per-band results, uncertainty, cost and downloadable evidence. The longer-term result is a separate engine ladder with paired openings, held-out tasks and enough games to support meaningful comparisons. Neither step requires inventing dispersion in a chart. Both require being explicit about what the measurement does and does not cover.
